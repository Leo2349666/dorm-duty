# 寝室值日排班系统

打开链接就能用的寝室值日排班工具。不用登录、不用注册，手机和电脑都能开，微信里点开也能正常用。

核心规则一句话说清：**按周期轮换，周期内每天安排相同**。一周 7 天里甲都负责阳台，下一周换丙负责阳台。

## 一、快速开始

```bash
npm install
npm run dev
```

浏览器打开终端里提示的地址（默认 http://localhost:5173）。想用手机试，用 `npm run dev -- --host` 启动，然后手机连同一个 WiFi 访问电脑的局域网 IP。

其他常用命令：

| 命令 | 作用 |
|---|---|
| `npm run dev` | 本地开发 |
| `npm run build` | 类型检查 + 打包到 `dist/` |
| `npm run preview` | 本地预览打包结果 |
| `npm run typecheck` | 只做类型检查 |
| `npm run verify` | 跑排班算法自检（25 项，验证轮换规则没被改坏） |

**不配任何东西就能直接用。** 不填环境变量时，系统运行在「纯本地模式」，数据存在浏览器里，推到 GitHub Pages 打开链接照样能用。想开多设备同步再去看[第八节](#八开启多设备同步supabase)。

## 二、需求分析与功能清单

### 目标

给一个 5 人寝室做一个"打开就能用"的值日排班页。使用者不会为了看今天谁倒垃圾去注册账号，所以**无登录、无密码、链接直达**是硬约束。

### 功能清单

| 模块 | 功能 | 状态 |
|---|---|---|
| 房间 | 公寓 → 楼栋联动选择，输入房间号，本机保存房间列表，可删除记录 | ✅ |
| 房间 | 房间已存在时直接进入，不重复创建 | ✅ |
| 成员 | 默认 5 人，增、删、改、拖拽排序、启用 / 停用 | ✅ |
| 值日内容 | 默认阳台 / 地面 / 倒垃圾 / 洗手台 / 浴室，增、删、改、拖拽排序、配色 | ✅ |
| 周期设置 | 周期天数（默认 7）、开始日期、结束日期 | ✅ |
| 自动排班 | 一键生成开始日期到结束日期的全部排班 | ✅ |
| 手动调整 | 点某天调整，三种范围：仅今天 / 仅本周期 / 从此以后 | ✅ |
| 日历 | 月视图 + 周视图，颜色标记，点日期看详情 | ✅ |
| 历史记录 | 记录自动排班和手动调整，含调整前后对比、操作时间 | ✅ |
| 统计 | 每人值日次数、每项被分配次数、公平度 | ✅ |
| 导出 | JSON（备份）、CSV（Excel）、图片（发群） | ✅ |
| 首页 | 突出显示当前周期谁负责什么，高亮"我"的那一行 | ✅ |
| 同步 | 同房间多设备实时同步（需配置 Supabase） | ✅ |
| 导航 | 移动端底部 5 个 tab，桌面端左侧边栏 | ✅ |

### 明确做了取舍的地方

- **不做打勾完成**。首页和日历纯粹是"看谁干啥"，不记录完成状态。
- **不做 PDF 导出**。浏览器端生成中文 PDF 必须内嵌一个 3~8MB 的中文字体文件，会让微信里首次加载明显变慢，收益不划算。
- **不做账号体系**。房间就是身份，同名房间即同一份数据。
- **不做房间口令**。值日表不是敏感信息，先保持零门槛。

## 三、技术方案与架构

### 技术栈

| 层 | 选择 | 为什么 |
|---|---|---|
| 框架 | React 18 + TypeScript | 生态成熟，类型安全 |
| 构建 | Vite 5 | 快，打包产物小 |
| 样式 | Tailwind CSS 3 | 移动端优先写起来最直接 |
| 路由 | React Router 6 的 **HashRouter** | GitHub Pages 刷新不会 404 |
| 状态 | Zustand | 比 Context 少一堆样板代码 |
| 拖拽 | @dnd-kit | **原生 HTML5 拖拽在手机上完全不工作**，必须用这个 |
| 日期 | dayjs | 体积小 |
| 图片导出 | html2canvas | 动态加载，不用时不下载 |
| 后端 | Supabase（可选） | 免费、国内可直连、自带 Realtime |

### 核心：一套代码，两种模式

```
                    ┌─────────────────────┐
                    │   React 页面 / 组件  │
                    └──────────┬──────────┘
                               │ 只认 DataAdapter 接口
                    ┌──────────▼──────────┐
                    │   DataAdapter 接口   │  src/data/types.ts
                    └──────────┬──────────┘
                    ┌──────────┴──────────┐
          没配环境变量 │                     │ 配了环境变量
        ┌───────────▼──────────┐  ┌────────▼──────────────┐
        │    LocalAdapter      │  │   SupabaseAdapter     │
        │  localStorage 存储    │  │  匿名登录 + Realtime   │
        │  单设备可用           │  │  多设备实时同步        │
        └──────────────────────┘  └───────────────────────┘
```

启动时读 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_ANON_KEY`：

- 两个都有值 → 云端模式
- 任意一个为空 → 本地模式

**页面代码完全不知道背后是哪一个。** 以后想升级成多设备同步，只需要加环境变量、重新构建，一行业务代码都不用改。

`supabase-js` 是用动态 `import()` 引入的，纯本地模式下这个包根本不会被下载，微信里首次打开能少拉一百多 KB。

### 同步状态与离线

界面上常驻一个小圆点，告诉你数据到底传没传上去：

| 状态 | 含义 |
|---|---|
| 仅本机 | 没配云端，数据只在浏览器里 |
| 已同步 | 云端已连上，数据是最新的 |
| 同步中 | 正在读写 |
| 离线 | 写云端失败了，改动进了本地队列，联网后自动补传 |

离线时的处理逻辑：所有写操作都是「先更新界面 → 再写云端」，失败就把这次操作压进本地队列（存 localStorage，关掉浏览器也不丢），监听 `online` 事件，网络恢复后按顺序重放。**不会静默丢数据。**

### 实时同步怎么做的

进入房间后用 Supabase Realtime 订阅该房间的 `members`、`duty_items`、`schedules`、`change_logs`、`rooms` 变化，收到推送就重新拉一次数据。推送做了 400ms 防抖，避免连续变更时反复请求。

没有订阅 `assignments` 表——因为每次改写排班都是「先删 schedules 行再插入」，`assignments` 会跟着级联删除重建，所以订阅 `schedules` 就够了，少订阅一张表能明显减少手机上的推送开销。

## 四、数据模型

完整的建表 SQL 在 [`supabase/schema.sql`](supabase/schema.sql)，直接粘贴到 Supabase 的 SQL Editor 里执行即可。

| 表 | 字段 | 说明 |
|---|---|---|
| `rooms` | id, apartment, building, room_number, name, period_days, start_date, end_date, rotation_mode, created_at | `(apartment, building, room_number)` 唯一 |
| `members` | id, room_id, name, order_index, active, deleted_at, created_at | `order_index` 直接决定轮换次序 |
| `duty_items` | id, room_id, name, order_index, color, deleted_at, created_at | color 用于颜色标签 |
| `schedules` | id, room_id, date, cycle_index, created_at | `(room_id, date)` 唯一，一天一行 |
| `assignments` | id, schedule_id, member_id, duty_item_id, is_manual, note | is_manual 标记这天被手改过 |
| `change_logs` | id, room_id, date, action, summary, before_json, after_json, created_at | 历史记录 |

### 两个关键设计

**一、软删除。** `members` 和 `duty_items` 都有 `deleted_at` 字段，删除只是打标记，行本身还在。这样历史排班里的 `member_id` 永远指向一条真实存在的记录，姓名查得到，也不会破坏外键。文档要求的"删除成员后历史记录保留"就是靠这个实现的。

**二、排班按天存。** 虽然规则是"周期内每天相同"，理论上一个周期存一行就够了，但按天存有两个好处：日历月视图可以直接按日期区间查询；"仅今天调整"这类需求天然有地方落。

容量估算：一学期 18 周约 127 天 → 127 条 schedules + 635 条 assignments。Supabase 免费版 500MB，完全无压力。

## 五、自动排班算法

### 规则回顾

1. 只按周期轮换，周期内每天安排完全相同
2. 第 0 个周期：成员顺序与值日内容顺序一一对应
3. 之后每个周期，成员顺序**循环右移一位**再对应
4. 人数 < 项数：多出来的项继续按成员顺序循环分配（一人多岗）
5. 人数 > 项数：多出来的人与前面的项共同负责（多人共担）
6. 最后一周不足周期天数时按实际天数生成，人员沿用该轮结果

### 核心洞察：一个公式统一覆盖所有情况

把两个列表按 `max(人数, 项数)` 的长度同时循环展开：

```
第 i 个槽位：  成员 = rotated[i % n]      值日项 = items[i % m]
其中 i 从 0 到 max(n, m) - 1
rotated = 成员列表循环右移 cycleIndex 位
```

这一个公式同时满足"每人每周期至少一项"和"每项都有人"，不需要为人数多、人数少写两套分支。

### 伪代码

```
输入：成员列表 members（按 order_index 升序，只取启用的）
      值日内容 items（按 order_index 升序）
      开始日期 startDate、周期天数 periodDays、结束日期 endDate

函数 rotateRight(list, k):
    n ← list.length
    shift ← (k mod n + n) mod n
    return [ list[(i - shift + n) mod n] for i in 0..n-1 ]

函数 buildCycleSlots(members, items, cycleIndex):
    n ← members.length ;  m ← items.length
    rotated ← rotateRight(members, cycleIndex)
    slots ← []
    for i in 0 .. max(n, m) - 1:
        slots.push( { 成员: rotated[i mod n], 值日项: items[i mod m] } )
    return slots

函数 buildPlans(members, items, startDate, periodDays, from, to):
    plans ← []
    for date in from .. to:
        cycleIndex ← floor( (date - startDate) / periodDays )
        plans.push( { date, cycleIndex, slots: buildCycleSlots(members, items, cycleIndex) } )
    return plans
```

### 用你文档里的例子验证

成员 `[甲, 乙, 丙]`，值日项 `[阳台, 地面, 倒垃圾]`：

| 周期 | 轮换后的成员序列 | 结果 |
|---|---|---|
| 第 1 轮 | `[甲, 乙, 丙]` | 甲阳台、乙地面、丙倒垃圾 |
| 第 2 轮 | `[丙, 甲, 乙]` | 丙阳台、甲地面、乙倒垃圾 |
| 第 3 轮 | `[乙, 丙, 甲]` | 乙阳台、丙地面、甲倒垃圾 |

完全符合需求文档第 5 条。

### 人数与项数不相等时

**4 人 5 项**（人少项多，`max = 5`）：

```
(甲,阳台) (乙,地面) (丙,倒垃圾) (丁,洗手台) (甲,浴室)
```

每人都有一项，甲多担一项。关键在于**多担的那个人每轮都会换**——连排 4 轮之后，四个人的总次数完全相同。

**6 人 5 项**（人多项少，`max = 6`）：

```
(甲,阳台) (乙,地面) (丙,倒垃圾) (丁,洗手台) (戊,浴室) (己,阳台)
```

阳台由甲和己共担，同样每轮轮换共担者，连排 6 轮后人人次数相同。

这两种情况系统会自动处理，**不会拦着你操作**，只在界面上温和提示一句"可考虑新增值日内容"。

### 手动调整的三种范围

点日历上任意一天，或者首页的「快速换班」，会弹出调整面板，底部可以选范围：

| 范围 | 行为 | 适用场景 |
|---|---|---|
| **仅今天** | 只改这一天的分工，其它日子照旧，后续周期也不受影响 | 某人今天临时有事 |
| **仅本周期** | 本轮的所有天一起改，下轮起恢复原样 | 这周就这么定下来 |
| **从此以后** | 改写轮换基线，本轮及之后每一轮都按新顺序轮换 | 某人以后固定负责某项 |

「从此以后」的实现值得一提。用户改完后，系统从编辑结果反推出**新的成员顺序基线**，使得用新基线跑出来的这一轮刚好等于用户编辑的结果，然后从这一轮开始往后重排。数学上是把"第 k 轮轮换后的序列"反向旋转 k 位：

```
新基线 = rotateLeft(第 k 轮的序列, k)
```

举例：基线 `[甲, 乙, 丙]`，第 2 轮时轮换结果是 `[丙, 甲, 乙]`。用户把它改成了 `[甲, 乙, 丙]`，那么新基线 = `rotateLeft([甲,乙,丙], 1)` = `[乙, 丙, 甲]`。验证一下：用新基线跑第 2 轮 = `rotateRight([乙,丙,甲], 1)` = `[甲, 乙, 丙]` ✓ 与用户编辑完全一致。

这段逻辑有专门的回归测试（`npm run verify` 的最后三行）。

## 六、页面结构与路由

全部走 HashRouter（URL 里带 `#`），刷新和直接访问都不会 404。

| 路由 | 页面 | 入口 |
|---|---|---|
| `#/` | 房间列表 | 全屏 |
| `#/add` | 添加房间（公寓 → 楼栋联动） | 全屏 |
| `#/room/:id` | 值日（当前周期，底部带导出区） | 底部 tab 1 |
| `#/room/:id/calendar` | 日历（月 / 周切换） | 底部 tab 2 |
| `#/room/:id/members` | 成员管理 | 底部 tab 3 |
| `#/room/:id/items` | 值日内容管理 | 底部 tab 4 |
| `#/room/:id/settings` | 设置 | 底部 tab 5 |
| `#/room/:id/stats` | 统计与公平度 | 设置页入口 / 桌面端侧边栏 |
| `#/room/:id/history` | 历史记录 | 设置页入口 / 桌面端侧边栏 |

移动端底部固定 5 个 tab（值日 / 日历 / 成员 / 内容 / 设置），统计和历史收在设置页里，避免底部塞太挤。桌面端（≥768px）自动切换成左侧边栏，7 项全部展开。

### 首页文案怎么定的

首页显示的是**当前周期**。因为周期内每天安排相同，显示一整轮和显示"今天"其实是同一件事，所以首页永远只有一屏内容。

标题按周期长度自适应，**日期范围永远显示**（日期是唯一真正准确的信息）：

| 周期天数 | 主标题 | 副标题 |
|---|---|---|
| 1 天 | 今日值日 | 9月13日 周日 |
| 7 天 | 本周值日 | 第 3 周 · 9月14日 – 9月20日 |
| 14 天 | 本轮值日 | 第 3 轮（两周）· 9月14日 – 9月27日 |
| 其他（如 5、10、30 天） | 本轮值日 | 第 3 轮（5 天）· 9月14日 – 9月18日 |

如果今天正好不在排班范围内（还没开始或者早就结束了），首页**只显示"当前无排班"**，不会拿最近一轮的安排来充数 —— 避免把过期的安排误当成今天的任务。这种情况下会给出「去设置排班周期」和「查看日历」两个入口。

### 布局适配

- 移动端：顶部固定栏 + 内容区 + 底部固定导航，内容区随页面滚动
- 桌面端（≥768px）：左侧边栏**固定不动**，右侧内容区独立滚动，两边互不影响
- 桌面端内容宽度上限 1024px、左右各留 80px（约占视口 5.6%），避免大屏两侧空出一大片

### 导出图片的排版为什么和别处不一样（重要）

导出图片是把一块**离屏渲染**的卡片交给 html2canvas 截图生成的。这块卡片在排版上和项目其它地方刻意不同，原因是一个实测出来的库行为：

> **html2canvas 画文字时存在固定的基线偏移** —— 文字会比它所在的盒子中心低几个像素。
> 实测：14~15px 字号下偏低约 7px；换成 `height` + `line-height` 显式对齐、换成别的字体，偏差都一样，所以这是库自身的问题，不是 CSS 写法问题。

后果很直观：**只要用"图形"（色块、圆角标签、色条）去配"文字"，导出图里文字就会贴着色块底边、和色条对不齐**。浏览器里是对的（`Range.getClientRects()` 显示文字行盒和色块中心都是 48.0），但导出的 PNG 是错的。

所以这块卡片采用**纯文字驱动**的排版：

- 颜色只用「彩色圆点字形 `●`」和「彩色人名文字」表达，**没有任何色块背景**
- 圆点也是文字，和值日项名称、人名走同一套文字渲染，天然对齐
- 行与行之间只用 1px 虚线分隔（横线的位置和文字没有对齐关系）

实测结果：同一行内 `人名 - 值日项` 的中心偏差为 **0.0px**，圆点因为字形本身不是正圆，偏差在 1.5px 以内。

**不要**把这里的圆点换回 `<div>` 色块、也不要把人名套回带背景色的圆角标签 —— 那样"标签与颜色错位"会立刻回来。改完请跑一次「导出图片」亲眼确认。

## 七、部署到 GitHub Pages

### 第 1 步：改 base 路径（重要，漏了会白屏）

打开 `vite.config.ts`，把 `base` 改成你的仓库名：

```ts
export default defineConfig({
  base: '/你的仓库名/',   // 末尾的斜杠不能少
  ...
})
```

默认写的是 `/dorm-duty/`。如果你建的仓库就叫 `dorm-duty`，这一行不用动。

> 为什么必须改？GitHub Pages 的项目站点地址是 `https://用户名.github.io/仓库名/`，如果 `base` 还是 `/`，页面会去 `https://用户名.github.io/assets/xxx.js` 找文件，那里什么都没有，结果就是白屏。

### 第 2 步：推送到 GitHub

```bash
git init
git add .
git commit -m "寝室值日排班系统"
git branch -M main
git remote add origin https://github.com/你的用户名/dorm-duty.git
git push -u origin main
```

### 第 3 步：打开 Pages

仓库页面 → **Settings** → 左侧 **Pages** → 把 **Source** 改成 **GitHub Actions**。

（这一步不能漏。默认是 "Deploy from a branch"，那样不会执行我们写的 workflow。）

### 第 4 步：等部署完成

推送后会自动触发 `.github/workflows/deploy.yml`。去仓库的 **Actions** 标签页能看到进度，绿勾之后访问：

```
https://你的用户名.github.io/dorm-duty/
```

以后每次 `git push` 到 main 分支，都会自动重新构建部署。

### 第 5 步（可选）：配置云端同步的环境变量

如果要用 Supabase，去 **Settings → Secrets and variables → Actions → Variables** 标签页，新建两个 **Repository variable**（注意是 Variables 不是 Secrets，这两个值本来就是公开的）：

| 名称 | 值 |
|---|---|
| `VITE_SUPABASE_URL` | 你的 Supabase Project URL |
| `VITE_SUPABASE_ANON_KEY` | 你的 Supabase anon public key |

加完之后再去 Actions 手动触发一次部署（选 workflow，点 Run workflow），或者随便推一次代码。

**不配置这两个变量也完全没问题**，构建会走纯本地模式，页面照样能打开。

### 常见问题

| 现象 | 原因 |
|---|---|
| 打开一片空白 | `base` 没改成仓库名 |
| 打开一片空白（base 改对了） | Settings → Pages 的 Source 还是 "Deploy from a branch" |
| 刷新页面 404 | 你在用 BrowserRouter。本项目用的是 HashRouter，正常不会出现；如果出现了检查 `src/App.tsx` 里的 `HashRouter` 有没有被改掉 |

## 八、开启多设备同步（Supabase）

这一步是可选的。不配置的话系统是纯本地模式，功能全都能用，只是数据不跨设备。

### 第 1 步：建项目

1. 打开 https://supabase.com ，用 GitHub 账号登录
2. New project，随便起个名字，区域建议选 **Southeast Asia (Singapore)**，国内访问相对快
3. 等两三分钟，项目初始化完成

### 第 2 步：建表

1. 左侧菜单 **SQL Editor** → New query
2. 把 [`supabase/schema.sql`](supabase/schema.sql) 的全部内容粘贴进去
3. 点 **Run**，看到 "Success. No rows returned" 就对了

这个脚本会建 6 张表、加索引、开启行级安全（RLS）、打开 Realtime 推送。

### 第 3 步：打开匿名登录

左侧 **Authentication** → **Sign In / Providers** → 找到 **Anonymous** → 打开开关。

> 这一步非常容易漏。不开的话前端调用匿名登录会直接报错。
> 如果界面上找不到这个开关，可以在 SQL Editor 里执行：`update auth.config set enable_anonymous_sign_ins = true;`

### 第 4 步：拿密钥

左侧 **Project Settings** → **API**，复制两个值：

- **Project URL**，形如 `https://xxxxxxxx.supabase.co`
- **anon public** key（很长的一串 JWT）

### 第 5 步：填进项目

本地开发的话，把 `.env.example` 复制成 `.env`，填进去：

```
VITE_SUPABASE_URL=https://xxxxxxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGciOi...
```

线上部署的话，按[第七节第 5 步](#第-5-步可选配置云端同步的环境变量)配到 GitHub 的 Variables 里。

重启 `npm run dev`，回到首页，顶部的小圆点应该变成绿色的"已同步"。

### 怎么验证同步成功了

用两台设备（或者一个手机 + 一个浏览器的无痕窗口）打开同一个链接，都输入相同的公寓、楼栋、房间号，然后在一台上改个成员名字。另一台如果一两秒内跟着变了，就说明同步通了。

### anon key 放在前端安全吗

安全。anon key 本来就是设计成公开的，真正的权限控制靠 RLS 策略。本项目的策略是"已登录用户可读写"，而用户是通过匿名登录获得身份的，所以能挡住直接拿 anon key 绕过前端来爬数据的脚本。

**但要清楚这个边界**：房间是由"公寓 + 楼栋 + 房间号"明码标识的，知道房间号的人可以进来。值日表不是敏感信息，所以默认没做额外口令。如果你需要，可以后续加一个"房间口令"字段做二次校验。

## 九、微信内打开的注意事项

前端已经做了这些适配，保证微信里能正常用：

- 用 **HashRouter**，微信里刷新和从聊天记录点进来都不会 404
- `index.html` 里放了首屏骨架动画，JS 还在加载时不会是一片纯白
- 构建目标降到 **ES2015**，兼容老版本 Android WebView
- `viewport-fit=cover` + `safe-area-inset-bottom`，全面屏手机底部导航不会被小黑条挡住
- 输入框字号统一 ≥16px，iOS 不会因为字号太小而自动放大页面
- 复制功能准备了 `navigator.clipboard` 和 `execCommand` 两条路，微信里 `navigator.clipboard` 经常是 undefined
- 拖拽用 @dnd-kit 的 TouchSensor，并加了 180ms 长按延迟——**原生 HTML5 拖拽在手机上完全不工作**，微信里更是拖不动

### 但有两个坑必须提前知道

**一、`xxx.github.io` 在国内是"时好时坏"的。** 微信内置浏览器打开 GitHub Pages 域名，可能加载缓慢、偶发打不开，或者被提示"非官方网页"。这是域名的问题，不是代码的问题。真要稳定，得绑一个自己的域名（在仓库 Settings → Pages → Custom domain 里填，然后在域名商加一条 CNAME 记录指向 `你的用户名.github.io`）。

**二、微信会拦截文件下载。** 导出 JSON / CSV / 图片时，点了可能没反应。系统里已经做了兜底：

- 导出图片会先把长图渲染出来给你看，**长按图片就能保存到相册**，这条在微信里是通的
- 另外提供了「复制 JSON」，复制到剪贴板后可以粘到备忘录里保存
- 也可以点右上角 "…" → 在浏览器中打开，然后用正常的下载流程

### 小技巧

部署好之后，在微信里把链接转发到寝室群，让室友点开一次，然后引导他们把页面**添加到桌面**（iOS 用 Safari 的"添加到主屏幕"，Android 用 Chrome 的"添加到主屏幕"）。这样它就变成一个图标，以后不用每次翻聊天记录找链接。

## 十、边界情况的处理策略

### 1. 成员退出、新成员加入

**新成员从下一个周期开始参与轮换，当前周期完全不动。** 添加成员后系统会自动从下一轮开始重排，并提示"将从 X 月 X 日起的下一轮开始参与值日"。这样室友已经执行的这一周不会被打乱。

退出优先用**停用**（保留在名单里、可以随时恢复），确实不会再回来再用**删除**。删除是软删除，历史记录里照样能查到这个人。

### 2. 某天有人请假

首页点「快速换班」，或日历里点那一天，把值日项换给别人，范围选**仅今天**。系统会在历史记录里留一条"XX 调整（仅当天）：倒垃圾：移除 甲；倒垃圾：加入 乙"。

如果这个人的某一项暂时没人接，也可以留空——系统只在自动排班时保证"每人至少一项"，手动调整时只会提示一句，不会拦着不让保存。

### 3. 值日项被删除后

软删除。已生成的排班和历史记录里这项仍然可见，只是不再参与新的排班。别人翻开上个月的历史，还能看到那天是谁擦的桌子。

### 4. 周期调整后，已生成的排班怎么办

- 只改**结束日期**：已有排班保留，重新生成时按新范围补齐或截断
- 改**开始日期**或**周期天数**：周期的划分方式整个变了，旧排班失去意义。系统会弹确认框明确告知"已生成的排班和手动调整会全部清空"，确认后才执行，然后需要重新生成

**不会静默清空数据**，这一点是刻意的。

### 5. 多设备同时修改

每次写操作后都会触发 Realtime 推送，另一台设备收到后自动重新拉取最新数据。推送做了 400ms 防抖，避免连续变更导致反复请求。

极端情况下两个人同时改同一天的排班，会出现"后写覆盖先写"。值日表这种场景下这个代价可以接受，不引入复杂的冲突解决机制。**如果某台设备显示"离线"，说明它的改动还没传上去，联网后会自动补传。**

### 6. 无网络时

写操作失败会把这次操作压进本地队列（存 localStorage），界面立即显示改动结果，小圆点变红显示"离线"。监听 `online` 事件，网络恢复后按顺序重放队列。用户在恢复网络前刷新页面也不会丢——队列是持久化的。

### 7. 房间不存在或创建失败

- 添加房间时服务器上已存在同名房间 → 直接进入，不重复创建
- 创建失败（网络问题等）→ 页面上直接显示具体错误原因，不会静默失败
- 打开一个已被删除的房间 → 显示加载状态后回到房间列表

### 8. 开始日期晚于结束日期

设置页会立即显示红字提示，保存按钮不生效，自动排班也会抛出明确错误。

### 9. 人数和项数不相等

系统自动处理（人少项多则循环分配，人多项少则多人共担），不拦着操作，只在界面上温和提示。详见[第五节](#五自动排班算法)。
